第 4 章 系统架构设计

考点定位：考试核心中的核心——综合知识、案例分析、论文三科全覆盖。 优先级：最高。芝士架构公开大纲列出架构专业课覆盖：系统架构设计、大数据架构、SOA、微服务、Redis、云原生、系统安全、架构评估、案例分析、论文写作；综合题重点含架构设计定义、五大架构风格、架构复用、ABSD、特定领域架构、质量属性与架构评估。

1. 知识地图

2. 核心知识

2.1 架构基础

  • 软件架构定义（IEEE 1471 / ISO 42010）：系统组织、构件、构件间交互与约束的集合，体现为「结构 + 行为 + 交互 + 设计决策」。
  • 4+1 视图模型：逻辑视图（功能/对象模型，面向用户）、进程视图（并发与同步，面向集成者）、物理视图（硬件拓扑，面向部署者）、开发视图（模块与分层，面向开发者）、场景视图（用例，统一其余 4 个视图的核心）。
  • 架构视图 ≠ 架构本身：视图是从某一视角对架构的投影。

2.2 架构风格（必背对比）

风格类别 代表风格 机制 优点 缺点 典型场景
数据流 批处理、管道-过滤器 数据依次流经处理单元 松耦合、易复用与并行 交互差、格式转换开销 编译器、日志/ETL 处理
调用/返回 主程序-子程序、面向对象、分层 显式调用与返回 结构清晰、易理解 层次过多性能下降、跨层调用破坏结构 业务系统、分层架构
独立构件 进程通信、事件驱动（隐式调用） 构件间通过消息/事件交互 解耦、可扩展、并发好 顺序与一致性难保证、调试难 GUI、消息中间件、通知系统
虚拟机 解释器、规则系统 通过解释引擎执行自定义语言/规则 灵活性极高 性能较低 规则引擎、脚本引擎
仓库（数据为中心） 数据库系统、黑板系统 共享中央数据结构 数据共享方便、适合复杂非结构化问题 中心依赖强、瓶颈风险 知识推理、数据密集型系统
特殊风格 闭环控制、C2、微内核、REST 反馈控制/消息总线/核心+插件/资源约束接口 各适其场景 需结合场景判断 嵌入式、IDE、Web API

答题范式：说明风格 → 列出构件与连接件 → 结合质量属性分析优点 → 指出代价与风险 → 给出适用场景。切忌只写「高性能、易扩展」等空话。

2.3 质量属性与质量属性战术（案例必答）

质量属性 含义 常用战术
性能 响应时间、吞吐量 缓存、并发、负载均衡、资源调度、减少计算开销
可用性 系统正常运行时间比例（MTBF 相关） 冗余、故障检测、故障转移、心跳、看门狗、降级
可修改性 变更成本与影响范围 模块化、高内聚低耦合、抽象层、信息隐藏、配置化
安全性 抵御攻击、保护数据与隐私 认证、授权、加密、审计、入侵检测、最小权限
可测试性 易于发现错误 可观察性、接口契约、依赖注入、模块化
易用性 用户学习与使用成本 一致性界面、反馈、撤销、用户培训
互操作性 与外部系统协同 标准协议、适配器、契约与数据转换

工程实践补充：质量属性之间存在冲突（如加密提升安全性但降低性能），架构设计本质是权衡（trade-off），需要在具体场景下量化取舍。

2.4 架构评估（高频易错）

方法 全称 核心 关注点
SAAM Software Architecture Analysis Method 基于场景，主要评估可修改性 最早的场景驱动评估方法
ATAM Architecture Tradeoff Analysis Method 基于场景，识别质量属性权衡，产出风险点/敏感点/权衡点 案例题最常考
CBAM Cost Benefit Analysis Method 在 ATAM 基础上加入成本-收益分析 决策经济性问题

四个关键概念（必考辨析）：

  • 敏感点（sensitivity point）：某个架构决策对某一质量属性有显著影响（如「缓存大小影响响应时间」）。
  • 权衡点（tradeoff point）：一个决策同时影响多个质量属性且方向相反（如「加密强度同时影响安全性与性能」）。
  • 风险点（risk point）：架构中可能导致不良后果的决策或潜在问题。
  • 非风险点（nonrisk point）：被认为安全的、不会产生负面后果的决策。

效用树（utility tree）：以「质量属性 → 属性精化 → 场景 → 优先级（H/M/L）」的树形结构，把模糊质量目标转成可评估的具体场景。

2.5 架构开发方法与复用

  • ABSD（基于架构的软件设计）：以商业目标、功能需求、质量需求三者共同驱动，自顶向下分解，迭代细化；强调在早期识别质量属性场景。三要素：视角与视图、用例与质量场景、架构风格。
  • DSSA（特定领域软件架构）：领域工程中形成的可复用架构，包含领域模型、参考架构、构件库；四阶段：领域分析 → 领域设计 → 领域实现 → 领域演化。
  • MDA（模型驱动架构）：CIM（计算无关模型）→ PIM（平台无关模型）→ PSM（平台相关模型）→ 代码，通过映射规则自动转换。

2.6 现代架构模式

模式 核心机制 优点 代价/风险
SOA 服务契约 + ESB 集成，SOAP/REST 跨系统复用、集中治理 ESB 单点瓶颈、协议较重
微服务 按业务能力拆分、独立部署、去中心化治理、注册发现、网关、熔断限流 独立演进、弹性伸缩、故障隔离 分布式复杂度（一致性、链路追踪、运维成本）
云原生 容器 + Kubernetes + Service Mesh + Serverless + DevOps 弹性、自动化、资源效率 学习曲线陡、平台依赖
事件驱动 生产者/消费者 + 消息代理 时空解耦、削峰填谷 最终一致性、消息重复与顺序
CQRS + 事件溯源 读写模型分离、以事件流作为状态来源 读写性能优化、可审计 复杂度高、最终一致
DDD 限界上下文、领域模型、聚合根 复杂业务建模清晰 对领域专家依赖高

微服务 vs SOA（必考对比）：微服务粒度更细、服务自治（独立数据与部署）、去中心化治理；SOA 粒度较粗、依赖 ESB 集中治理、强调复用。

2.7 架构演化

遗留系统改造四策略：淘汰（退休）、改造（重构/再工程）、集成（封装为服务）、继承（继续维护）。技术债务需通过重构、架构治理逐步偿还；迁移常用 strangler（绞杀者）模式、灰度与双跑。

3. 易混淆概念对比

对比项 关键区别
架构风格 vs 架构模式 风格是从实践中总结的宏观组织范式；模式是解决特定问题的可复用设计方案（更具体）
敏感点 vs 权衡点 敏感点影响一个属性；权衡点同时影响多个且方向冲突
风险点 vs 非风险点 风险点是有害决策；非风险点是已确认无害的决策
SAAM vs ATAM SAAM 侧重可修改性；ATAM 覆盖多质量属性并分析权衡
逻辑视图 vs 开发视图 逻辑视图面向功能（对象/类）；开发视图面向实现组织（模块/分层/构件）
微服务 vs SOA 独立部署与去中心化 vs ESB 集中集成

4. 考试重点

  1. 案例题：给出系统场景与质量属性要求，选择合适架构风格并论证（必须结合场景，不能只罗列优点）。
  2. ATAM 过程与产出：场景、效用树、风险点/敏感点/权衡点识别。
  3. 4+1 视图与对应干系人配对。
  4. 微服务拆分原则与分布式挑战（数据一致性、服务治理、可观测性）。
  5. 论文常考：论软件架构风格、论架构评估、论软件架构演化、ABSD、微服务/云原生。

5. 典型例题（原创模拟题）

例题 1（案例简答，原创模拟）：某电商系统在促销期间订单创建缓慢，要求架构师提出改进。经分析，商品详情信息频繁读取且变化少。请从质量属性战术角度给出建议，并指出可能引入的权衡点。

参考答案要点：① 质量属性定位为性能；② 采用缓存战术（热点商品详情缓存、CDN），配合连接池、异步化非关键流程（通知、统计）；③ 引入缓存带来数据一致性问题（时效性下降）与内存成本，即「性能提升 ↔ 一致性/成本」构成权衡点；④ 需通过失效策略（TTL + 主动失效）和监控缓解。

例题 2：在 ATAM 评估中，「将通信改为异步消息可提升可用性，但会使订单状态查询无法立即获得最新结果」属于（　）。 A. 风险点　B. 敏感点　C. 权衡点　D. 非风险点

答案：C。解析：一个决策同时影响可用性（正向）与一致性/正确性（负向），是典型权衡点。若只显著影响一个属性则是敏感点。

6. 记忆技巧

  • 4+1 视图：逻进物开 + 场景（「逻辑进程物理开发，场景串起四视图」）。
  • 五大风格：数据流、调用返、独立构、虚拟机、仓库（简称「流调独虚仓」）。
  • 评估四概念：敏感看单项，权衡看冲突，风险是将来，非风险已安心。
  • 架构演化四策略：淘改集继。

7. 随堂测试

  1. 管道-过滤器风格适合什么类型系统？主要缺点是什么？
  2. 效用树的作用是什么？
  3. 微服务相对 SOA 最本质的两个区别是什么？
参考答案 1. 适合数据流明确的批处理/格式转换系统（如编译器、ETL）；缺点是交互式差、数据格式转换开销大、错误传播处理复杂。 2. 将模糊的质量属性目标逐层细化为可评估、可排序的具体场景，并确定优先级，为架构评估提供依据。 3. 服务粒度更细且围绕业务能力；服务独立部署自治、治理去中心化（不依赖集中 ESB）。

8. 芝士架构资料补充（案例高频核心）

来源：《案例冲刺宝典》第 3、4、5、6、8 章与《公共知识红宝书》第 4 章。本节为案例第一题的高频区。

8.1 架构风格完整对照（★★★★★）

一级风格 二级风格 核心 典型场景
数据流 批处理 分步执行、整体传递、无并行 离线任务、BAT 脚本、传统编译器
数据流 管道-过滤器 前步输出作后步输入、可流水并行、不落盘 Unix Shell、编译器阶段处理
调用/返回 主程序/子程序 单线程控制、层次化 早期结构化程序
调用/返回 面向对象 封装、消息传递 Java/C# 应用
调用/返回 层次型 每层为上层服务、作为下层客户；接口只对相邻层可见 Web、数据库应用
调用/返回 C/S、B/S 二层 C/S 胖客户端；三层 C/S 加应用服务器；B/S 零安装 企业应用、Web 系统
以数据为中心 仓库 中央数据结构 + 一组独立构件 现代 IDE、数据仓库
以数据为中心 黑板 分级解空间、多知识源协同 语音/模式识别、专家系统
虚拟机 解释器 自定义语言解析执行、动态扩展 脚本引擎、规则引擎
虚拟机 规则系统 规则集 + 规则解释器 + 工作内存 专家系统、决策支持
独立构件 进程通信 独立过程 + 消息传递 分布式系统、微服务
独立构件 事件驱动 隐式调用、事件广播触发 GUI、工具集成、语法检查
特殊 C2 构件经连接件分层、强制自上而下通信 嵌入式、分布式应用
特殊 过程控制 反馈循环调节物理状态 空调控温、汽车巡航
  • 批处理 vs 管道-过滤器：批处理必须前一步整体结束后才开始、需落盘；管道-过滤器前面执行到一定阶段即可开始下一步、不落盘、性能更高。
  • 解释器 vs 面向对象（真题套路）：规则可修改性、灵活性解释器更强；性能面向对象略优（解释器多一层）。规则频繁变化场景选解释器。

8.2 九大必考质量属性（超级重点★★★★★）

案例常以选词填空考查”场景属于哪个质量属性”，对策需熟悉。

属性 描述 对策
性能 响应能力：处理事务时间或单位时间事务量 优先级队列、增加计算资源、减少计算开销、并发机制、资源调度
可靠性 应用错误/意外使用下维持功能的能力，用平均失效时间衡量 冗余（硬件/数据）、错误检测恢复（奇偶校验/CRC）、异常处理、备份恢复、负载均衡
可用性 正常运行时间比例：两次故障间时长或恢复正常速度 心跳机制、冗余系统（双机热备/集群）、快速恢复、内置监控预警、故障转移
安全性 向合法用户提供服务同时阻止非授权访问/拒绝服务；含机密性、完整性、不可否认性、可控性 认证、授权（RBAC）、加密、防火墙、IDS/IPS、审计日志
可修改性 快速高性价比变更的能力；含可维护性、可扩展性、结构重组、可移植性 模块化降低耦合、接口标准化、抽象封装、配置管理、版本控制
互操作性 与其他系统/环境交互的能力；不同语言系统间交互 标准协议接口（RESTful API/SOAP）、数据格式转换、中间件、服务注册发现、跨语言工具
可移植性 适应不同运行环境（OS/硬件/云）的能力 遵循标准协议/API、避免平台专有 API、抽象底层差异、兼容性测试
可测试性 易于发现缺陷、验证功能与性能 分层模块化、提供测试接口、状态值可访问
易用性 好学、好找、好操作、少犯错 统一交互规范、信息架构清晰、即时反馈、降低认知负荷、快捷操作、本地化、无障碍
  • 辨析口径：心跳检测组件在线状态，内置监视器偏预警；可靠性与可用性近十年未真正辨析，ISO/IEC 25010 中可用性是可靠性的子集，默认写”可用性”即可。
  • “发现错误并启用备用系统”“重定向到备用站点”“自动重启”等场景一律归为可用性。

8.3 质量属性场景六要素（超级重点★★★★★）

描述公式：刺激源 + 刺激 + 环境 + 制品 + 响应 + 响应度量（SEI 的 Bass/Clements/Kazman《软件架构实践》提出）。

要素 理论含义 白话 秒杀示例
刺激源 人、计算机系统或刺激器 测试参与者 大量用户
刺激 刺激到达时需考虑的条件 触发条件 双十一 0 点同时点击秒杀
环境 刺激发生时系统可能处于的状态 触发时对象状态 系统正常运行状态
制品 受刺激的模块或系统 测试对象 商品展示/购物车/订单模块
响应 激励到达后采取的行动 对象反应 快速处理请求并返回结果
响应度量 对响应进行度量的方式 如何衡量好坏 200ms 内响应、吞吐 500 QPS
  • 记忆技巧：左侧（刺激源、刺激）归为”刺激”，右侧（环境、制品、响应、响应度量）归为”响应”，先二分再展开。

六大属性场景描述表（曾考大题）：

属性 刺激源 刺激 环境 制品 响应 响应度量
可用性 系统内部/外部 疏忽、错误、崩溃、时间 正常→降级模式 处理器、通信信道、持久存储器、进程 检测/记录/通知事件、隔离故障、等待恢复 故障修复时间
可修改性 最终用户、开发人员、管理员 改变功能、扩容 设计时/编译时/构建时/运行时 用户界面、平台、环境、交互系统 修改且不影响其他功能 成本/努力/资金、对其他功能的影响
性能 用户请求、其他系统触发 事件到达 正常→超载模式 系统 处理刺激、改变服务级别 等待时间、期限、吞吐量、抖动、缺失率
可测试性 开发、测试、客户 分析/架构/设计/集成交付时触发 设计/开发/编译/部署时 设计、代码段、应用 提供状态值访问、计算值、测试环境 语句覆盖率、缺陷触发概率、测试时间、最长依赖链、环境准备时间
易用性 最终用户 想学习特性、有效使用 运行时或配置时 系统 友好界面、适应性设计、减少错误影响 用户满意度、成功操作占比
安全性 内部/外部个人或系统 试图访问修改数据、访问服务 系统所处网络环境 系统服务、数据 认证、授权、审计、加密、监控 检测、溯源、恢复

8.4 架构评估方法（★★★★★）

方法 描述 优点 缺点
调查问卷/检查表 借相关人员经验知识评估 充分利用经验 依赖主观推断
基于场景 分析架构对场景的支持程度（SAAM、ATAM 属此类） 系统评估特定场景 需详细定义场景、耗时
基于度量 建立质量属性与度量映射，从架构文档推导 客观、可量化 需精确度量方法与专业知识
  • SAAM（次重点）：主要分析可修改性；输入为问题描述、需求声明、架构描述；过程：场景开发→架构描述→单场景评估→场景交互评估→总体评估；是 ATAM 的基础。
  • ATAM（★★★★★）：在 SAAM 基础上发展，针对性能、安全性、可修改性、可用性，用效用树量化优先级再做折中。四阶段（迭代式）：场景和需求收集 → 架构视图和场景实现 → 属性模型构造和分析 → 权衡。论文答题可按”演示 → 调查和分析 → 测试 → 报告”四阶段展开。
  • 效用树：树根 → 质量属性 → 属性分类 → 质量属性场景（叶子）；默认四大属性为性能、安全性、可修改性、可用性；修剪保留通常不超过 50 个场景；优先级用（重要度 H/M/L，难易度 H/M/L）表示，如（H、L）表示重要且易实现。

8.5 评估四概念句式辨析（★★★★★）

概念 定义 句式特征
敏感点 一个或多个构件及其关系的特性 “对…的要求将影响…的设计”
权衡点 影响多个质量属性，是多个敏感点的综合 一个决策使 A 属性变好、B 属性变坏（如加密级别：安全性↑性能↓）
风险点 可能导致架构问题或无法满足质量属性的决策 “如果…，可能…，影响…”
非风险点 不会造成负面影响或影响可接受 “成熟稳定的方案，不会带来明显风险”
风险承担者 试图影响架构决策以实现目标的利益相关者 财务部门、销售部门
场景 从风险承担者角度对交互的简短描述，用刺激/环境/响应描述 “客户在公共 Wi-Fi 登录网银，需 10 秒内完成认证”

8.6 层次架构与反模式（★★★★★）

  • 污水池反模式（Sinkhole Anti-Pattern）：请求只是机械穿过各层（界面层转发→业务层转发→持久层简单 SQL），各层不承担职责。危害：层次隔离失效、结构不清、业务规则散落、可维护性降低。解决：层次开放——让适合处理的层直接处理，避免所有层都成转发层。
  • 表现层 MVC / MVP / MVVM：MVC 单向（View→Controller→Model→View）；MVP 双向（View↔Presenter↔Model，Presenter 主动更新 View）；MVVM 双向数据绑定（View↔ViewModel↔Model）。
  • 中间层 DomainModel-Service-Control：DomainModel 封装业务实体与核心逻辑；Service 协调跨领域操作（事务、权限）；Control 决定 Service 执行顺序，实现松耦合切换。
  • 数据访问模式：在线访问、DAO（封装数据源交互）、DTO（跨进程传输、无业务逻辑）、离线数据、ORM（对象关系映射）。在线访问性能优、可处理复杂查询但要求懂 SQL；ORM 降低开发成本但复杂查询困难、性能略逊。

8.7 物联网层次架构（★★★☆☆）

  • 感知层（传感器、RFID、二维码、摄像头、GPS、M2M 终端）→ 网络层（通信网、互联网、3G/4G、IPv6、网关）→ 应用层（行业智能化应用、物联网中间件、云计算）。
  • 设备接入协议对比：HTTP 请求/响应、通用但开销大；MQTT 发布/订阅、轻量适合弱网高频小数据；CoAP 请求/响应、适合受限节点。物联网设备特点：数量多、性能弱、网络不稳、上报频率高、单条数据小。
