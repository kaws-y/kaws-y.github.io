# 第 11 章 软件测试

> 优先级：中高。芝士架构公开大纲中架构论文知识包含「系统测试」「软件可靠性测试」主题。

## 2. 核心知识

### 2.1 测试基础与 V 模型

- **测试目的**：发现缺陷（不是证明程序无错）；成功的测试是发现了至今未发现错误的测试。
- **V 模型对应**：需求分析 ↔ 验收测试；概要设计 ↔ 系统测试；详细设计 ↔ 集成测试；编码 ↔ 单元测试。
- **测试原则**：尽早测试、穷尽测试不可能、缺陷集群（80% 缺陷在 20% 模块）、杀虫剂悖论（需定期更新用例）。

### 2.2 黑盒测试方法

| 方法 | 核心思想 | 典型应用 |
| --- | --- | --- |
| 等价类划分 | 将输入域划分为有效/无效等价类，每类取代表值 | 输入范围校验 |
| 边界值分析 | 重点测边界及边界附近（略小于、等于、略大于） | 数值范围、数组下标 |
| 判定表驱动 | 多条件组合 → 动作，用表格穷举规则 | 复杂业务规则 |
| 因果图 | 由原因-结果关系导出判定表 | 输入条件相互制约 |
| 错误推测 | 基于经验猜测易错场景 | 补充用例 |
| 正交试验 | 用正交表减少组合爆炸 | 多参数组合配置 |

### 2.3 白盒测试：逻辑覆盖强度（必考排序）

由弱到强：
1. **语句覆盖**：每条语句至少执行一次（最弱）。
2. **判定覆盖（分支覆盖）**：每个判定的真/假分支都至少执行一次。
3. **条件覆盖**：每个判定中每个条件的真/假值都至少取到一次。
4. **判定-条件覆盖**：同时满足判定覆盖与条件覆盖。
5. **条件组合覆盖**：每个判定中所有条件取值组合都至少出现一次。
6. **路径覆盖**：每条可能路径都至少执行一次（最强，但路径爆炸）。

> 注意：判定覆盖与条件覆盖互不包含（覆盖条件取值 ≠ 覆盖分支），这是常见陷阱。

### 2.4 测试层次

| 层次 | 测试对象 | 依据 | 主要方法 |
| --- | --- | --- | --- |
| 单元测试 | 模块/函数 | 详细设计 | 白盒为主（桩模块、驱动模块） |
| 集成测试 | 模块间接口与组装 | 概要设计 | 灰盒；自顶向下/自底向上/三明治 |
| 系统测试 | 完整系统（含软硬件） | 需求规格说明 | 黑盒为主；功能与非功能 |
| 验收测试 | 用户业务场景 | 用户需求/合同 | 用户参与；α 测试（开发方场地）、β 测试（用户场地） |

- **回归测试**：修改后重新执行部分或全部用例，确保未引入新缺陷；常借助自动化测试。
- **冒烟测试**：版本构建后先做基本功能快速验证，决定能否进入正式测试。

### 2.5 缺陷管理与专项测试

- **缺陷生命周期**：新建 → 分配 → 修复 → 验证 → 关闭（可能重开）；严重性（崩溃/严重/一般/轻微）vs 优先级（修复顺序）是两个不同维度。
- **性能测试**：负载测试（不同负载下表现）、压力测试（极限负载）、稳定性/疲劳测试（长时间）、并发测试。
- **可靠性测试**：通过统计失效数据评估 MTBF 等指标，验证可靠性目标（与第 14 章联动）。
- **自动化测试**：适合回归、冒烟、数据驱动、大批量重复场景；成本在于脚本维护，不适合一次性或探索性测试。

## 3. 易混淆概念对比

| 对比项 | 关键区别 |
| --- | --- |
| 黑盒 vs 白盒 | 黑盒不看内部代码（依据需求）；白盒分析程序内部逻辑（依据代码） |
| 判定覆盖 vs 条件覆盖 | 判定覆盖看分支真假都走到；条件覆盖看每个条件的取值都取到，互不包含 |
| α 测试 vs β 测试 | α 在开发方环境由用户参与；β 在用户真实环境由用户执行 |
| 单元测试 vs 集成测试 | 单元测模块内部逻辑（需桩/驱动）；集成测模块间接接口与协作 |
| 错误 vs 故障 vs 失效 | 错误（人）→ 故障/缺陷（代码）→ 失效（运行时可观察的偏离） |
| 负载测试 vs 压力测试 | 负载测试逐级加压观察表现；压力测试加到极限甚至超限找崩溃点 |

## 4. 考试重点

1. 给出程序流程图，判断某组测试用例达到哪种覆盖（最常见的综合题）。
2. 黑盒方法选择：输入范围 → 等价类 + 边界值；多条件组合 → 判定表/因果图。
3. 测试层次与 V 模型对应关系。
4. 缺陷严重性与优先级的区别。
5. 回归测试与自动化测试的适用边界。

## 5. 典型例题（原创模拟题）

**例题 1**：逻辑覆盖准则中，最强的是（　）。
A. 语句覆盖　B. 判定覆盖　C. 条件组合覆盖　D. 路径覆盖

**答案**：D。**解析**：路径覆盖要求每条可能路径都执行，通常强于条件组合覆盖（但程序中若存在不可达路径则无法实现）。强度排序：语句 < 判定/条件 < 判定-条件 < 条件组合 < 路径。

**例题 2**：某输入要求「年龄 18～60」，采用边界值分析时最合理的测试数据是（　）。
A. 18, 60　B. 17, 18, 19, 59, 60, 61　C. 0, 100　D. 30, 45

**答案**：B。**解析**：边界值分析取边界及边界两侧的值，B 覆盖了略小于、等于、略大于边界，最完整。

## 6. 记忆技巧

- 逻辑覆盖强度：**语 → 判 → 条 → 判条 → 组 → 路**（「语判条，判组路」）。
- V 模型对应：**需求验收、概设系统、详设集成、编码单元**。
- 黑盒方法：**等价边界打头阵，判定因果管组合，错误推测补经验**。

## 7. 随堂测试

1. 为什么说「测试能证明程序没有错误」是错误的？
2. 桩模块（Stub）与驱动模块（Driver）分别用于哪种测试方式？
3. α 测试与 β 测试的主要环境区别是什么？

<details>
<summary>参考答案</summary>

1. 测试只能发现已发现的错误，不能证明错误不存在（穷尽测试不可能）。
2. 自顶向下集成需要桩模块模拟下层；自底向上集成需要驱动模块模拟上层调用。
3. α 测试在开发方场所进行，β 测试在用户实际场所由用户执行。

## 8. 芝士架构资料补充

> 来源：《公共知识红宝书》第 5 章。

### 8.1 W / H / X 测试模型（★★★☆☆，2023 年已考）
三种模型讨论"测试如何做"，图不重要，重点记特点：

| 模型 | 定义 | 测试与开发关系 |
| --- | --- | --- |
| W 模型 | 在 V 模型基础上发展，测试与开发**同步** | 同步 |
| H 模型 | 测试活动**独立**，贯穿整个软件生命周期 | 独立 |
| X 模型 | 针对单独程序片段编码和测试，**频繁交接集成** | 交错 |

### 8.2 专项测试要点（★★★☆☆）
- **安全测试**：安全漏洞测试（扫描 XSS、SQL 注入、命令注入，工具如 BurpSuite）；TCP 端口测试（关闭非必要端口，仅保留业务必需端口如 80/443）；服务器端脚本漏洞检查（未授权脚本上传/修改、目录遍历、文件包含）；防火墙测试（验证规则拦截非法请求、限制流量、防御 DDoS 的有效性）。
- 功能测试、性能测试见前文；测试分类方法（黑盒/白盒各种具体方法）为本章重点★★★★★。
