# 第 2 章 需求工程

> 考点定位：综合知识高频；案例分析常考「需求获取方法选择与理由」「需求变更管理」；论文热点（论需求分析方法、论需求管理）。
> 优先级：高。芝士架构公开课程大纲将「需求工程」列为公共课重点，子模块为：需求获取、结构化分析、面向对象分析、需求定义和验证、需求管理。

## 1. 知识地图

| 子模块 | 核心考点 | 考查形式 | 优先级 |
| --- | --- | --- | --- |
| 需求获取 | 访谈、JRP、问卷、观察、原型、头脑风暴、文档分析 | 案例：方法选择及优势分析 | ★★★★★ |
| 需求分析 | 结构化分析（DFD/数据字典）、面向对象分析（UML） | 案例 + 选择 | ★★★★★ |
| 需求定义与规格说明 | SRS 内容、需求分类（功能/非功能/设计约束） | 选择题 | ★★★★ |
| 需求验证 | 评审、原型验证、测试用例导出 | 选择题 | ★★★ |
| 需求管理 | 变更控制、需求跟踪矩阵、需求基线、版本管理 | 案例高频 | ★★★★★ |

## 2. 核心知识

### 2.1 需求分类

- **功能需求**：系统必须完成的功能（做什么）。
- **非功能需求**：性能、安全性、可靠性、可用性、可维护性等质量属性（做得怎样）。
- **设计约束**：技术平台、标准规范、法规、预算、工期等限制条件。
- 补充：业务需求（组织目标）、用户需求（用户视角）、系统需求（技术视角）自顶向下逐层细化。

### 2.2 需求获取方法（案例必考）

| 方法 | 适用情形 | 优势 | 局限 |
| --- | --- | --- | --- |
| 用户访谈 | 少数关键干系人、需深挖 | 深入、可追问 | 覆盖面小、耗时 |
| JRP 联合需求计划 | 多方干系人需快速达成一致 | 高度组织的群体会议，冲突当场解决，达成共识快 | 组织成本高、需主持人控场 |
| 问卷调查 | 用户量大、分布广 | 覆盖面广、成本低、便于统计 | 问题固定、无法追问、回收率风险 |
| 实地观察 | 用户说不清实际操作 | 发现隐性需求、贴近真实流程 | 耗时、霍桑效应 |
| 原型法 | 需求模糊、界面密集 | 可视可交互、反馈具体 | 易误解为最终产品 |
| 文档分析 | 已有系统或制度文档 | 快速建立业务背景 | 文档可能过时、与实际不符 |
| 头脑风暴 | 需求初期发散创意 | 激发新思路 | 结果需后续收敛验证 |

> **案例答题要点**：先说明项目处于什么阶段、需求来源有什么特点，再按「覆盖来源广度 + 消除冲突 + 用户参与」三条线索选方法并逐条说明理由。

### 2.3 需求分析方法

- **结构化分析（SA）**：面向数据流，核心产物是 **DFD 数据流图 + 数据字典 + 加工说明**。DFD 从顶层（上下文图）逐层分解到子图，元素只有四种：外部实体、加工、数据存储、数据流。
- **面向对象分析（OOA）**：以对象/类为核心，用 UML 用例图捕获功能需求，类图描述领域模型，顺序图/活动图描述交互与流程。
- **面向问题域分析**：强调对问题域的直接建模，减少分析与实现的语义鸿沟。

### 2.4 需求规格说明书（SRS）

SRS 是需求定义阶段的核心交付物，应做到：**正确、完整、一致、可验证、可追踪、无二义性**。典型结构：引言（目的/范围/术语）、总体描述（功能/用户/约束）、具体需求（功能需求、非功能需求、接口需求）、附录。

### 2.5 需求验证

主要手段：**需求评审**（正式技术评审，最常用）、**原型验证**、**模型一致性检查**、**基于需求的测试用例设计**（测试前置，可提前发现不可测需求）。

### 2.6 需求管理

- **需求基线**：经评审确认的需求版本，作为后续开发与变更的基准。
- **需求变更控制**：提交变更申请 → 影响分析（范围/进度/成本/质量）→ CCB 审批 → 实施与验证 → 更新基线与跟踪矩阵。
- **需求跟踪矩阵（RTM）**：双向追踪「用户需求 → 系统需求 → 设计 → 代码 → 测试用例」，用于评估变更影响范围。

## 3. 易混淆概念对比

| 对比项 | 关键区别 |
| --- | --- |
| 需求获取 vs 需求分析 | 获取是「收集原始诉求」，分析是「建模、分类、发现冲突与遗漏」 |
| 用户需求 vs 系统需求 | 用户需求是用户视角的期望表述；系统需求是其技术化、可验证的精确描述 |
| 需求验证 vs 需求确认 | 验证检查「需求文档是否正确完整」；确认由用户确认「是否是其真正想要的」 |
| JRP vs 头脑风暴 | JRP 结构化、有主持人与议程、产出决策；头脑风暴发散、不即时评判 |
| DFD vs 流程图 | DFD 描述「数据在哪里被加工、流向哪里」，不强调控制顺序；流程图强调处理步骤与控制流 |

## 4. 考试重点

1. 案例题：给出多来源需求冲突的场景，要求说明选用哪些获取方法、各自优势，以及如何消除冲突。
2. 选择题：JRP 的优势（关键时刻：高度组织的群体会议、多方参与、当场解决冲突）。
3. 需求变更流程顺序：影响分析 → CCB 决策 → 更新基线/矩阵。
4. 需求跟踪矩阵的作用：双向追踪、变更影响分析、覆盖率检查。
5. SRS 质量属性中「可验证性」常被偷换为「可修改性」，需注意辨析。

## 5. 典型例题（原创模拟题）

**例题 1**：某企业销售平台改造涉及管理层、销售、仓储、财务等多方，需求来源分散且存在术语冲突。项目组希望在短时间内让各方对需求达成一致。最适合的需求获取方法是（　）。
A. 问卷调查　B. 用户访谈　C. 联合需求计划（JRP）　D. 文档分析

**答案**：C。**解析**：题干三个线索——多方干系人、需求冲突、快速达成一致，正对应 JRP 的优势。问卷适合面广但无法当场消除冲突；访谈深度够但覆盖窄；文档分析无法解决冲突。

**例题 2**（简答，原创模拟）：需求基线已确定后，客户提出新增报表导出功能。请简述正确的处理流程。

**参考答案要点**：① 提交书面变更申请；② 进行影响分析（对范围、进度、成本、质量、已有架构的影响）；③ 提交 CCB 评审决策（批准/拒绝/推迟）；④ 批准后更新 SRS、需求基线与需求跟踪矩阵，并同步设计与测试；⑤ 验证变更实现并关闭变更记录。

## 6. 记忆技巧

- 获取方法五字诀：**访（谈）问（卷）观（察）原（型）会（JRP）**。
- 需求工程五步：**获 → 分 → 定 → 验 → 管**（获取、分析、定义、验证、管理）。
- 变更处理链：**申请 → 影响分析 → 审批 → 实施 → 回写矩阵**（「影审实回」）。

## 8. 芝士架构资料补充

> 来源：《公共知识红宝书》第 2 章、《案例冲刺宝典》第 1 章。★越多越重要。

### 8.1 结构化分析模型总览（超级重点★★★★★）
- 基本思想：**自顶向下、逐层分解**。
- **数据字典是分析模型核心**，围绕它有三个模型：数据模型（ER 图）、功能模型（**DFD**）、行为模型（**状态转换图 STD**）。

### 8.2 DFD 完整规则（★★★★★）
- 四种基本符号：数据流（带名箭头）、加工（圆圈）、数据存储（两条平行线）、外部实体（方框）。
- **关键规则**：数据存储要被外部实体使用，必须经过加工（不可直连）。
- 两套记号集：Gane & Sarson 方法、Yourdon & Coad 方法——图"对不上"多因记号集不同。
- **扩充符号**（软考考过）：与 `*`、或 `+`、异或 `⊕`。
  - 与：所有输入都到达才加工 / 结束时同时产生所有输出。
  - 或：任一输入到达即可加工 / 至少产生其中一个输出。
  - 异或：仅当其中一个到达才加工 / 仅产生其中一个输出。
- **层次**：顶层图把整个系统表示为唯一加工，画出所有外部实体与进出数据流；再逐层分解加工。

### 8.3 DFD 平衡原则（★★★★★，案例高频"找茬"）
1. **父子图平衡**：两层 DFD 中数据流**个数一致、方向一致**。
2. **子图内部平衡**（四种典型错误）：

| 错误 | 特征 |
| --- | --- |
| 黑洞 | 加工只有输入没有输出 |
| 奇迹 | 加工只有输出没有输入 |
| 灰洞 | 输入不足以产生输出（挂羊头卖狗肉） |
| 数据存储异常 | 正常应既有读流又有写流 |

- 答题模板：先写父子图平衡（个数/方向一致），再写每张图内部平衡（每个加工都有输入与输出，避免黑洞/奇迹/灰洞）。

### 8.4 状态转换图 STD（★★★☆☆）
- 本质即 UML 状态图，属行为图；三大概念：状态（初态/终态）、事件（转移/动作）、并发状态机。
- 符号：初态=黑圆点，终态=黑圆点外加圆（双圈），中间状态=圆角四边形，状态转换=带箭头线。

### 8.5 UML 2.5 的 14 种图（★★★★★）
- **结构图（7 种）**：类图、对象图、包图、组合结构图、构件图、部署图、剖面图。
- **行为图（7 种）**：用例图、活动图、状态机图、顺序图、通信图、定时图、交互概览图。
- 易错点：**用例图在 UML 2.x 属于行为图**；记住结构图 7 种，其余都是行为图。

### 8.6 用例图关系辨析（★★★★★）

| 关系 | 含义 | 箭头方向 |
| --- | --- | --- |
| 包含 include | 基础用例必然调用另一用例（必选复用） | 由基础用例指向被包含用例 |
| 扩展 extend | 在特定条件下扩展基础用例（可选） | 由扩展用例指向基础用例 |
| 泛化 generalization | 父子用例/参与者之间的一般-特殊关系 | 由特殊指向一般 |

### 8.7 案例真题套路（★★★★★）
- **DFD 选词填空**：从外部实体与数据流方向反推加工（如"安全员提供指标数据→项目指标填报"）。
- **状态图事件填空**：沿状态迁移链按题干动作语义逐一匹配（按下启动→增加动力，按运行→开始程序等）。
- 需求定义与需求验证原书标注为非重点，但需求管理（变更控制、需求跟踪）为重点。
