# 07 锁机制、消息队列与秒杀

> 来源：《案例冲刺宝典》第 17、18、19 章。均为重点★★★★★。

## 一、锁机制

### 1. 为什么需要锁（★★★★★）
并发场景下保证共享资源的一致性（如库存扣减、订单状态），避免出现超卖、重复扣减等问题。

### 2. 常见锁类型（★★★★★）

| 类型 | 说明 |
| --- | --- |
| 乐观锁 / 悲观锁 | 悲观锁假设冲突必然发生、先加锁；乐观锁假设冲突少、提交时校验版本 |
| 共享锁 / 排他锁 | S 锁（读）可共存；X 锁（写）独占 |
| 本地锁 / 分布式锁 | 单 JVM 内（synchronized/ReentrantLock）vs 跨进程（Redis/数据库/ZooKeeper） |

### 3. 乐观锁 vs 悲观锁（★★★★★）
- **悲观锁**：适合写多读少、冲突频繁；实现：数据库 `select ... for update`、synchronized。
- **乐观锁**：适合读多写少、冲突少；实现：版本号字段（`version`）或 CAS，提交时 `where version = old`，失败重试。

### 4. 实际场景锁方案（★★★★★）

| 方案 | 适用 | 特点 |
| --- | --- | --- |
| synchronized 本地锁 | 单 JVM | 简单，分布式环境失效 |
| 数据库行锁 `select for update` | 强一致、并发不高 | 可靠但性能低、易死锁 |
| Redis 分布式锁 | 分布式高并发 | SETNX + 过期时间 + 唯一值防误删；需考虑锁续期、单点问题 |
| 数据库乐观锁（version） | 冲突少的分布式 | 性能好，失败需重试 |

## 二、消息队列与异步架构

### 1. 为什么需要 MQ（★★★★★）
- **异步解耦**：生产者不必同步等待消费者，服务间解耦。
- **削峰填谷**：平滑突发流量，保护后端系统。
- 顺序保证、最终一致性、削峰后异步处理。
- **引入 MQ 的代价**：系统可用性依赖 Broker、消息丢失/重复/顺序问题、运维复杂度上升。

### 2. 核心概念（★★★★★）
- Producer（生产者）、Consumer（消费者）、Message（消息）、Broker（消息服务器）。
- Topic（主题，发布订阅）、Queue（队列，点对点）、Partition（分区，并行与顺序保证）。
- **点对点模式**：一条消息只被一个消费者消费；**发布订阅模式**：一条消息被多个订阅者消费。
- ConsumerGroup（消费组）：组内竞争消费、组间广播。
- ACK/NACK + offset：消费确认机制，保证消息可靠消费与位点管理。
- Push（Broker 主动推，实时性好）vs Pull（消费者主动拉，可控性好）。
- **JMS**（Java 消息服务规范，点到点/发布订阅两种模型）vs **AMQP**（高级消息队列协议，网络线级协议，跨语言）。

### 3. MQ 常见生产问题（★★★★★）

| 问题 | 处理 |
| --- | --- |
| 消息丢失 | 生产端确认（confirm）、Broker 持久化、消费端 ACK 后手动提交 |
| 重复消费 | 消费端幂等设计（唯一 ID + 去重表 / 状态机） |
| 死信队列 DLQ | 多次重试失败的消息转入死信队列，人工处理或补偿 |
| 顺序性 | 同一业务键路由到同一分区（分区内有序） |
| 消息积压 | 扩容消费者、临时消费者迁移、限流上游 |

- **MQ 与分布式事务**：本地消息表 + MQ 实现最终一致性（业务与消息同本地事务落库，异步投递）。
- 常见 MQ 对比：Kafka（高吞吐、日志流、大数据场景）、RabbitMQ（灵活路由、AMQP）、RocketMQ（事务消息、金融电商）、ActiveMQ。

## 三、秒杀系统设计（★★★★★）

### 1. 核心痛点
瞬时超高并发、超卖问题、库存一致性、接口防刷、数据库压力。

### 2. 整体架构分层（★★★★★）

| 层次 | 设计要点 |
| --- | --- |
| 访问层 | CDN 静态化页面、限流（令牌桶）、防刷验证码、按钮置灰 |
| 中间转发层 | Nginx 限流、负载均衡、请求排队 |
| 服务层 | 服务拆分、限流降级、令牌机制（获取秒杀资格） |
| Redis 扣库存 | **Redis 预扣库存**（原子操作/Lua 脚本），避免直接打到数据库 |
| 消息队列层 | 异步下单：扣库存成功后发消息，消费者异步创建订单 |
| 数据层 | 最终落库、数据库兜底校验、事务保证订单一致性 |

- 核心思路：**层层过滤 + Redis 预扣 + MQ 异步 + 数据库最终一致**，把高峰流量挡在数据库之外。
