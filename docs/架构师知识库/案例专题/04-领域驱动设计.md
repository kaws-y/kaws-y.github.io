# 04 领域驱动设计 DDD

> 来源：《案例冲刺宝典》第 10 章。整体次重点★★★☆☆，但引申概念多为重点★★★★★。
> 核心主张：软件结构围绕**业务模型**组织，用**统一语言**与**清晰边界**应对复杂业务。

## 记忆主线：大的边界 → 小的边界 → 代码边界

## 1. 大的边界（业务版图边界）

| 概念 | 含义 | 电商示例 |
| --- | --- | --- |
| 领域 | 系统要解决的业务问题空间 | 电商交易 |
| 子域 | 领域中相对独立的问题区域 | 商品、下单、支付、库存、营销、售后 |

**子域三类（★★★★★）**：

| 类型 | 含义 | 策略 | 示例 |
| --- | --- | --- | --- |
| 核心子域 | 差异化竞争力所在 | 做深模型、持续演进 | 优惠计算引擎、履约协同 |
| 通用子域 | 可替代的成熟能力 | 复用成熟方案 | 统一登录、短信、通用支付 |
| 支撑子域 | 介于两者之间 | 视情况投入 | 内容运营、活动页搭建 |

## 2. 小的边界（团队协作边界）

- **统一语言（★★★★★）**：业务与研发共同使用的一套术语，落实到代码命名、接口字段、测试用例、文档、监控指标。示例："取消订单"（未支付时）与"关闭订单"（超时/风控/库存不足）必须明确区分，用 `OrderStatus`、`CancelReason`、`CloseReason` 体现。
- **限界上下文（★★★★★）**：DDD 中心概念——在明确边界内模型与语言保持一致；跨边界同名不同义，通过契约协作。电商可划出：商品上下文、交易上下文、营销上下文、库存上下文、支付上下文、履约物流上下文。
  - 反面示例：把优惠计算直接写进订单类，营销规则变化（双十一、周年庆、叠加券）就要改订单算价逻辑 → 订单模型被营销规则**污染**。
- **上下文映射（★★★☆☆）**：描述上下文间集成方式——客户/供应商、顺从者、**防腐层 ACL**、共享内核。
  - **防腐层（★★★★★）**：用翻译/适配层隔离外部模型，防止污染核心领域模型。示例：对接第三方支付时，用 ACL 把渠道特有状态码翻译成统一的"支付成功/失败/待确认"领域概念，换渠道只需替换 ACL。

## 3. 代码边界（★★★★★）

| 要素 | 含义 | 电商示例 |
| --- | --- | --- |
| 实体 Entity | 以**身份标识**区分，属性可变而身份不变 | 订单（orderId）、商品（productId） |
| 值对象 | 无身份标识，仅由属性值定义（原文仅在实体段引用此分类） | 地址、金额 |
| 聚合与聚合根 | **一致性边界**；外部通过聚合根统一入口修改，保证业务不变式 | 订单聚合（以 Order 为根），约束"已支付不可改金额""关闭后不可发货" |
| 领域服务 | 操作涉及多个聚合、难归属单一实体时承载业务规则 | 优惠分摊 `PromotionApportionService` |
| 领域事件 | 表示领域内发生的重要业务事实，用于边界内外解耦传播 | `PaymentSucceeded` |
| 仓储 Repository | 以"集合"方式获取/保存聚合，隐藏持久化细节 | `OrderRepository.findById/save` |
| 工厂 Factory | 创建复杂聚合，隐藏构造与校验逻辑 | `OrderFactory` 生成订单号、固化价格快照 |
| 应用编排 | 应用层负责用例编排（权限、加载聚合、调用领域方法、持久化、发布事件）；领域层负责业务规则本身 | "支付订单"流程编排属应用层；"订单能否支付"属领域层 |

## 4. 答题要点
DDD 案例常给出复杂业务系统，要求识别限界上下文、子域类型或领域模型要素。答题时按"大边界（子域划分）→ 小边界（上下文/统一语言/防腐层）→ 代码边界（实体/聚合/服务/事件/仓储）"三层展开，结合具体业务举例。
