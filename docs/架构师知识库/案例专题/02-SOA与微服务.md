# 02 面向服务架构 SOA 与微服务

> 来源：《案例冲刺宝典》第 5、9 章。超级重点★★★★★。

## 1. SOA 定义（★★★★★）
SOA 是一种粗粒度、松耦合的服务架构，服务通过定义良好的**契约**（接口）与**消息**交互，独立于底层平台与编程语言。目标：复用、 interoperability（互操作）、业务流程组合。

## 2. SOA / 微服务 / 单体对比（★★★★★）

| 维度 | 单体架构 | SOA | 微服务 |
| --- | --- | --- | --- |
| 拆分粒度 | 不拆分 | 粗粒度（服务/子系统级） | 细粒度（业务能力级） |
| 治理方式 | 无 | 集中治理（ESB） | 去中心化治理 |
| 通信 | 进程内调用 | SOAP/ESB 为主 | REST/gRPC 轻量协议 |
| 数据存储 | 单一数据库 | 可共享数据库 | 每服务独立数据 |
| 部署 | 整体部署 | 部分独立 | 独立部署 |
| 优点 | 简单、开发快 | 复用、集成异构系统 | 独立演进、弹性、故障隔离 |
| 缺点 | 难扩展、改动影响大 | ESB 单点瓶颈、复杂 | 分布式复杂度、运维成本高 |

## 3. 服务注册模式与关键协议（★★★★★）
- **服务注册**：服务提供者向注册中心发布服务，消费者从注册中心发现服务。
- **UDDI**：统一描述、发现和集成——服务注册与发现的标准（SOA 三要素之一）。
- **WSDL**：Web 服务描述语言——描述服务接口、操作、参数、返回值（SOAP 服务的契约）。
- **SOAP**：基于 XML 的消息交换协议，严格、重量级，支持 WS-* 规范。
- **REST 规范/风格**：表述性状态转移——
  - 资源（Resources）用 URI 标识；
  - 通过 HTTP 方法（GET/POST/PUT/DELETE）操作资源；
  - 无状态（Stateless）；
  - 可缓存、统一接口、分层系统。
  - 轻量、易理解，逐渐成为主流。

## 4. ESB 模式（★★★★★）
- **ESB（企业服务总线）**：SOA 的核心基础设施，提供服务注册、协议转换、消息路由、编排、安全、监控等能力。
- 优点：解耦服务间直接依赖、集中治理异构系统。
- 缺点：可能成为性能瓶颈与单点故障；总线逻辑过重违背服务自治。

## 5. SOA 设计原则（★★★★★）
服务无状态、服务契约明确、服务可复用、服务自治、服务可组合、服务粒度适中、标准化接口。

## 6. 微服务架构实践（SpringCloud 技术栈，★★★★★）

| 组件 | 作用 |
| --- | --- |
| **Nacos** | 服务注册与发现 + 配置中心（AP，自我保护机制） |
| **OpenFeign** | 声明式远程调用，屏蔽底层 HTTP 细节（看似本地调用实为远程） |
| **Gateway** | 统一入口：路由转发、鉴权、跨域、限流、日志、灰度、协议转换 |
| **Sentinel** | 服务保护：流量控制、熔断降级、系统负载保护 |
| **Ribbon/LoadBalancer** | 客户端负载均衡 |

- **服务拆分原则**：按业务能力/领域边界拆分（DDD 限界上下文），高内聚低耦合，避免过细。
- **集群部署**：多实例 + 负载均衡，配合注册中心实现故障转移。
- **Sentinel 流控**：QPS 限流、线程数限流；**熔断降级**：慢调用比例/异常比例触发熔断，避免雪崩。

## 7. 典型例题套路（★★★★★）
给出企业系统集成场景，要求对比 SOA 与微服务选型，或在性能、可修改性、可用性维度分析。答题要点：结合场景的异构程度、团队规模、变更频率、运维能力说明取舍。
