## 2. 核心知识

### 2.1 软件生命周期模型（考试核心）

**原理**：生命周期模型是对软件开发活动的组织方式，本质区别在于「需求何时冻结」「风险何时暴露」「交付如何切分」。

| 模型 | 核心特征 | 优点 | 缺点 | 典型场景 |
| --- | --- | --- | --- | --- |
| 瀑布 | 阶段线性顺序，需求先行冻结 | 管理简单、文档完整 | 风险后置，需求变更代价高 | 需求明确、技术成熟 |
| 原型 | 快速构建可运行模型收集反馈 | 缓解需求不明 | 原型易被当作正式产品、质量易被忽视 | 需求模糊、界面密集 |
| 增量 | 分批交付可用版本 | 早交付、风险分散 | 需良好架构支撑增量 | 需求可分模块 |
| 螺旋 | 每轮含目标设定、风险分析、开发验证、规划 | 风险驱动 | 复杂、依赖风险评估能力 | 大型高风险项目 |
| V 模型 | 开发阶段与测试阶段逐级对应 | 测试前置、可追溯强 | 灵活性差 | 高可靠、强验证项目 |
| 喷泉 | 面向对象、迭代无严格阶段边界 | 适合 OO、阶段可交叉 | 管理难度大 | 面向对象项目 |
| RUP | 用例驱动、架构为中心、迭代增量；四阶段（初始/细化/构造/交付） | 统一过程框架 | 裁剪成本高 | 大型 OO 项目 |
| 敏捷 | 迭代短周期、自组织团队、持续交付、拥抱变化 | 响应变化快 | 对客户参与和团队要求高 | 需求变化快、小规模团队 |

**Scrum 三角色五事件**：PO（产品负责人，管 Product Backlog）、 Scrum Master（移除障碍）、开发团队；Sprint、Sprint Planning、Daily Scrum、Sprint Review、Sprint Retrospective。**XP 实践**：结对编程、测试驱动开发（TDD）、持续集成、重构、简单设计、集体代码所有权。

### 2.2 软件过程改进：CMM 与 CMMI

- **CMM 五级**：初始级（混乱）→ 可重复级（项目级管理）→ 已定义级（组织级标准过程）→ 已管理级（量化管理）→ 优化级（持续改进）。
- **CMMI 两种表示**：阶段式（成熟度等级 1～5，整体评估）与连续式（能力等级 0～3，按过程域评估）。
- 记忆：CMM 问「组织整体到第几级」，CMMI 连续式问「某个过程域能力多强」。

### 2.3 软件质量属性（ISO/IEC 9126 六特性）

功能性、可靠性、易用性、效率、可维护性、可移植性。每个特性下含子特性（如可靠性含成熟性、容错性、易恢复性）。**注意**：性能、安全性在架构领域单独强调（见第 4 章）；9126 中「效率」对应性能，「功能性」包含适合性、准确性、互操作性、安全保密性。

### 2.4 配置管理

- **配置项（CI）**：源代码、文档、数据、工具等纳入管理的实体。
- **基线（Baseline）**：经正式评审后冻结的配置项集合，变更须走变更控制流程。
- **版本控制**：仓库、分支、标签；**变更控制**：CCB（变更控制委员会）审批。
- **配置状态报告 / 配置审计**：前者记录状态，后者验证完整性与一致性。

### 2.5 软件复用与软件产品线

- 复用层次：代码复用 → 构件复用 → 架构复用 → 领域复用（DSSA：特定领域软件架构）。
- **软件产品线**：共同产品线架构 + 可变点管理，实现大规模复用；核心资产库是基础。

## 3. 易混淆概念对比

| 对比项 | 关键区别 |
| --- | --- |
| 瀑布 vs V 模型 | V 模型强调测试与开发阶段一一对应、测试计划提前编写；瀑布只强调阶段顺序 |
| 原型 vs 增量 | 原型目的是澄清需求，通常丢弃或重构；增量目的是交付可用功能，逐次累积 |
| CMM 可重复级 vs 已定义级 | 可重复级是「项目有管理」，已定义级是「组织有统一标准过程」 |
| 基线 vs 里程碑 | 基线是配置项冻结状态；里程碑是项目进度检查点 |
| 软件质量保证（SQA）vs 软件测试 | SQA 面向过程审计与预防；测试面向产品缺陷发现 |

## 4. 考试重点

1. 给出一段项目描述（需求是否明确、风险高低、客户参与度）选择最合适的生命周期模型。
2. 判断某做法是敏捷还是瀑布实践；Scrum 角色职责配对。
3. CMMI 等级判定：有定量度量 → 已管理级（4 级）；有组织标准过程 → 已定义级（3 级）。
4. 质量特性归类：容错性属于可靠性，互操作性属于功能性。
5. 配置管理中「基线变更必须经过 CCB 审批」是常见正确选项。

## 5. 典型例题（原创模拟题）

**例题 1**：某项目需求尚不明确，客户无法完整描述界面与流程，团队计划先做一个可运行界面模型供客户确认，再逐步完善。最适合的生命周期模型是（　）。
A. 瀑布　B. 原型　C. V 模型　D. 螺旋

**答案**：B。**解析**：核心线索是「需求不明确 + 可运行界面模型确认」，这是原型模型的典型目的。V 模型强调测试对应；螺旋强调风险分析；瀑布要求需求预先冻结。

**例题 2**：某组织已建立统一的软件过程标准，各项目按标准裁剪执行，但尚未建立量化的质量目标。按 CMM，该组织处于（　）。
A. 初始级　B. 可重复级　C. 已定义级　D. 已管理级

**答案**：C。**解析**：组织级标准过程 = 已定义级（3 级）；「项目有管理但无组织标准」才是可重复级；「量化管理」才是已管理级（4 级）。

## 6. 记忆技巧

- 生命周期模型口诀：**瀑原形螺增，V 测喷面对，RUP 用例驱动，敏捷拥抱变化**。
- CMM 五级：**初、重、定、管、优**（「重」= 可重复，「定」= 已定义）。
- ISO 9126 六特性：**功可易效维移**（功能、可靠、易用、效率、维护、移植）。

## 8. 芝士架构资料补充

> 来源：《公共知识红宝书》第 1 章。星级为原书标注。

### 8.1 软件工程三要素与 PDCA（★★★☆☆）
- 软件工程 = **方法 + 工具 + 过程**。
- PDCA 循环：**P** 软件规格说明 → **D** 软件开发 → **C** 软件确认 → **A** 软件演进。

### 8.2 软件开发方法分类（★★★★★）

| 分类维度 | 具体方法 |
| --- | --- |
| 开发风格 | 自顶向下、自底向上 |
| 性质 | 形式化方法、非形式化方法 |
| 适应范围 | 整体性方法、局部性方法 |

### 8.3 形式化方法与净室软件工程 CSE（★★★☆☆）
- **形式化方法**：用严格数学模型与形式化语言描述需求/设计/行为，通过逻辑推理或模型检测证明"必然正确"；仍需与传统测试结合。
- **净室软件工程 CSE**：本质是一种形式化方法，理论基础为**函数理论**（首要：完备性、一致性、正确性）与**抽样理论**（统计抽样推断可靠性）。
- 四步骤：统计过程控制下的增量式开发 → 基于函数的规约 + 盒子结构 → 正确性验证 → 统计测试与软件认证。

### 8.4 逆向工程相关概念辨析（★★★☆☆）

| 概念 | 含义 | 判别线索 |
| --- | --- | --- |
| 逆向工程 | 从代码在低层抽象上重建高层表示，**设计恢复**过程 | "分析程序、恢复设计" |
| 重构 | 同一抽象层内转换描述形式 | "同层改结构" |
| 设计恢复 | 借工具抽取数据/总体/过程设计信息 | "借助工具抽取" |
| **再工程** | **逆向工程 + 新需求 + 正向工程**，产生新版本 | "修改、重构、升级" |
| 正向工程 | 从设计恢复信息出发改变/重构系统以改善质量 | "从设计到代码" |

- 逆向工程抽象层次（低→高）：实现级（抽象语法树、符号表）→ 结构级（调用图、结构图）→ 功能级（程序段功能及关系）→ 领域级（与应用领域概念对应）。口诀：**实现→结构→功能→领域**。

### 8.5 基于构件的软件工程 CBSE（★★★★★，超级重点）
- **构件六特性**（Sommerville）：可组装性、可部署性、文档化、独立性、标准化、无外部可见状态。
- **构件五分类**：独立而成熟的构件、有限制的构件、适应性构件、装配的构件、可修改的构件。
- **三种组装**：顺序组装（A 结果传给 B，构件互不调用）、层次组装（一构件直接调另一构件，需接口兼容）、叠加组装（多构件叠加为新构件，接口为原接口组合）。
- **接口不兼容三类型**：参数不兼容（操作名同、参数类型/数目不同）、操作不兼容（操作名不同）、操作不完备（提供接口是请求接口的子集或反之）。
- **提供接口**用圆形表示，**请求接口**用半箭头表示；接口兼容是层次组装的前提。

### 8.6 生命周期模型细节（★★★★★）
- **瀑布模型**（Royce 1970）：需求分析定义 → 系统设计 → 实现与单元测试 → 集成与系统测试 → 运行维护；缺点是依赖早期需求调查、不能适应变化。
- 按需求确定程度选型：需求完全确定 → 瀑布；初始仅能提供基本需求 → 喷泉、螺旋、统一过程、敏捷；以形式化方法为基础 → 变换模型。
